# Сценарии использования (Use Cases)

## 1. Назначение документа

Документ описывает взаимодействие заявителя, системы и оператора при подаче, проверке и рассмотрении заявок на получение государственной поддержки промышленными предприятиями.

Сценарии определяют основные шаги процесса, предусловия, результаты и альтернативные ветки обработки.

## 2. Акторы

| Актор | Описание |
|---|---|
| Заявитель | Представитель промышленного предприятия, который создаёт и отправляет заявку, отслеживает её статус и при необходимости вносит исправления |
| Система | Выполняет валидацию данных, получает сведения из внешних источников, запускает скоринг, рассчитывает маршрут заявки и сохраняет результаты |
| Оператор | Проверяет материалы заявки и принимает окончательное решение в пределах предоставленных полномочий |
| Внешние сервисы | Предоставляют сведения о юридическом лице, налоговой задолженности, процедурах банкротства и результатах скоринга |
| Модуль 2 | Получает сведения об одобренных проектах для мониторинга их исполнения |
| Модуль 3 | Получает финансовые условия одобренных проектов для контроля отчётности |

## 3. Статусы заявки

| Статус | Описание |
|---|---|
| `DRAFT` | Заявка создана, но ещё не отправлена |
| `SUBMITTED` | Заявка отправлена заявителем |
| `DATA_CHECK` | Система выполняет автоматические проверки |
| `NEEDS_REVISION` | Заявка возвращена заявителю на доработку |
| `UNDER_REVIEW` | Заявка находится на рассмотрении оператора |
| `APPROVED` | Оператор одобрил заявку |
| `REJECTED` | Заявка отклонена |

Технические статусы ошибок интеграций и ожидания повторных запросов необходимо согласовать с системными требованиями. Ошибка внешнего сервиса сама по себе не является основанием для отклонения заявки.

## 4. UC-01. Подача заявки на государственную поддержку

**Основной актор:** Заявитель.

**Цель:** Создать и отправить заявку на получение государственной поддержки.

**Предусловия:**
- заявитель имеет доступ к системе;
- заявитель располагает ИНН предприятия;
- система доступна для работы.

**Триггер:** Заявитель начинает создание новой заявки.

### Основной сценарий

1. Заявитель открывает форму подачи заявки.
2. Заявитель вводит ИНН предприятия.
3. Система проверяет формат ИНН.
4. Система запрашивает сведения о предприятии из доступного внешнего источника.
5. Система отображает полученные сведения для проверки заявителем.
6. Заявитель проверяет предзаполненные поля и дополняет обязательные сведения.
7. Заявитель прикладывает необходимые документы, если они предусмотрены формой.
8. Заявитель отправляет заявку.
9. Система выполняет валидацию обязательных полей и форматов данных.
10. Система сохраняет заявку и присваивает ей уникальный идентификатор.
11. Система присваивает заявке статус `SUBMITTED`.
12. Система уведомляет заявителя об успешной отправке.

**Постусловия:**
- заявка сохранена;
- заявке присвоен уникальный идентификатор;
- заявка доступна для дальнейшей обработки;
- заявитель может отслеживать её статус.

### Альтернативные сценарии

**A1. Некорректный ИНН**

1. Система обнаруживает ошибку формата или контрольного значения ИНН.
2. Система отображает сообщение об ошибке.
3. Заявитель исправляет ИНН.
4. Сценарий продолжается с шага 2 основного сценария.

**A2. Не удалось получить сведения о предприятии**

1. Система фиксирует ошибку внешнего сервиса.
2. Система уведомляет заявителя о невозможности автоматически заполнить данные.
3. Система предлагает повторить запрос или продолжить заполнение вручную, если это допускается требованиями.
4. Если обязательные сведения получить или подтвердить невозможно, отправка заявки блокируется до устранения проблемы.

**A3. Не заполнены обязательные поля**

1. Система обнаруживает незаполненные или некорректные поля.
2. Система отображает список ошибок.
3. Заявитель исправляет данные.
4. Система повторно выполняет валидацию.

**A4. Ошибка сохранения заявки**

1. Система сообщает о невозможности завершить операцию.
2. Система фиксирует техническую ошибку.
3. Заявитель получает возможность повторить отправку.
4. Повторная отправка не должна приводить к созданию дубликата заявки.

## 5. UC-02. Автоматическая проверка заявки

**Основной актор:** Система.

**Участники:** Внешние сервисы.

**Цель:** Проверить сведения о предприятии и определить дальнейший маршрут заявки.

**Предусловия:**
- заявка успешно отправлена;
- заявке присвоен уникальный идентификатор;
- обязательные поля прошли первичную валидацию.

**Триггер:** Система начинает обработку отправленной заявки.

### Основной сценарий

1. Система переводит заявку в статус `DATA_CHECK`.
2. Система получает сведения о юридическом статусе предприятия.
3. Система запрашивает сведения о налоговой задолженности.
4. Система запрашивает сведения о процедурах банкротства.
5. Система выполняет предусмотренную правилами проверку по РНП.
6. Система сохраняет результаты проверок.
7. Система определяет, обнаружены ли стоп-факторы.
8. Если стоп-факторы не обнаружены, система запрашивает результат скоринга.
9. Система проверяет корректность полученного скорингового балла.
10. Система определяет дальнейший маршрут заявки согласно `business-rules.md`.
11. Система сохраняет результат автоматической оценки и основание маршрутизации.
12. Система уведомляет заявителя об изменении статуса, если такое уведомление предусмотрено требованиями.

### Результаты автоматической оценки

| Условие | Результат обработки |
|---|---|
| Обнаружен стоп-фактор | Автоматическое отклонение согласно учебным бизнес-правилам |
| Стоп-факторов нет, скоринг от 0 до 59 | Отклонение согласно учебным бизнес-правилам |
| Стоп-факторов нет, скоринг от 60 до 79 | Перевод в `UNDER_REVIEW` |
| Стоп-факторов нет, скоринг от 80 до 100 | Перевод в `UNDER_REVIEW` с рекомендацией к одобрению |

**Важно:** высокий скоринговый балл не означает автоматического одобрения. Окончательное решение принимает оператор.

### Альтернативные сценарии

**A1. Внешний сервис недоступен**

1. Система фиксирует ошибку интеграции.
2. Система выполняет повторный запрос согласно согласованной политике.
3. Если получить результат не удалось, система сохраняет информацию о незавершённой проверке.
4. Заявка не отклоняется только по причине недоступности сервиса.
5. Дальнейшая обработка выполняется согласно согласованным правилам ожидания или ручного рассмотрения.

**A2. Получены неполные или противоречивые сведения**

1. Система сохраняет полученный ответ.
2. Система фиксирует, какие сведения не удалось подтвердить.
3. Система не трактует отсутствие данных как подтверждение отсутствия стоп-фактора.
4. Заявка направляется на дополнительную обработку согласно согласованным требованиям.

**A3. Получен некорректный результат скоринга**

1. Система проверяет, входит ли балл в допустимый диапазон от 0 до 100.
2. Если значение некорректно или отсутствует, система фиксирует ошибку.
3. Система не использует некорректный балл для маршрутизации.
4. Заявка остаётся в обработке до получения корректного результата или выполнения согласованного альтернативного сценария.

**Постусловия:**
- результаты завершённых проверок сохранены;
- обнаруженные стоп-факторы зафиксированы;
- при наличии корректного результата скоринга определён маршрут заявки;
- все ошибки интеграций зарегистрированы.

## 6. UC-03. Рассмотрение заявки и принятие решения

**Основной актор:** Оператор.

**Цель:** Рассмотреть заявку и зафиксировать окончательное решение.

**Предусловия:**
- автоматические проверки завершены либо заявка передана на рассмотрение по согласованному альтернативному сценарию;
- оператор авторизован;
- оператор имеет необходимые полномочия.

**Триггер:** Заявка поступает в очередь рассмотрения.

### Основной сценарий

1. Оператор открывает список заявок, доступных для рассмотрения.
2. Оператор выбирает заявку.
3. Система отображает сведения о предприятии, данные заявки, результаты проверок и скоринговый балл.
4. Оператор изучает материалы и основания автоматической оценки.
5. Оператор принимает решение в пределах своих полномочий.
6. Если заявка соответствует условиям одобрения, оператор выбирает решение `APPROVED`.
7. Если заявка не соответствует условиям программы, оператор выбирает решение `REJECTED` и указывает основание.
8. Система проверяет допустимость перехода в выбранный статус.
9. Система сохраняет решение, дату и время, идентификатор оператора и основание решения.
10. Система обновляет статус заявки.
11. Система уведомляет заявителя о результате.
12. При одобрении система передаёт предусмотренные сведения в Модуль 2 и финансовые условия в Модуль 3.

### Альтернативные сценарии

**A1. Возврат на доработку**

1. Оператор обнаруживает недостатки или неполноту материалов.
2. Оператор выбирает действие «Вернуть на доработку».
3. Оператор указывает замечания для заявителя.
4. Система сохраняет замечания и переводит заявку в `NEEDS_REVISION`.
5. Система уведомляет заявителя.
6. Заявитель исправляет данные и повторно отправляет заявку.
7. Система сохраняет историю изменений и запускает необходимые проверки повторно.

**A2. Оператор отклоняет заявку**

1. Оператор выбирает решение об отклонении.
2. Оператор указывает основание решения.
3. Система сохраняет решение и его основание.
4. Система переводит заявку в `REJECTED`.
5. Система уведомляет заявителя.

**A3. Оператор не имеет необходимых полномочий**

1. Система проверяет права пользователя.
2. Система запрещает выполнение операции.
3. Система отображает сообщение об отсутствии необходимых прав.
4. Система регистрирует событие отказа в доступе.

**A4. Ошибка при сохранении решения**

1. Система фиксирует ошибку сохранения.
2. Система не подтверждает успешное принятие решения, если оно не было надёжно сохранено.
3. Оператор получает сообщение о необходимости повторить операцию.
4. Повторная операция не должна создавать дублирующие решения.

**A5. Не удалось передать данные в Модуль 2 или Модуль 3**

1. Система сохраняет окончательное решение.
2. Система фиксирует ошибку передачи данных.
3. Система сохраняет сведения о необходимости повторной отправки.
4. Система повторяет передачу согласно согласованной политике интеграции.
5. Ошибка передачи не должна приводить к повторному принятию решения по заявке.

**Постусловия:**
- решение сохранено;
- история принятия решения доступна для аудита;
- заявитель уведомлён о результате;
- при одобрении сформированы данные для передачи в смежные модули.

## 7. Общие бизнес-ограничения сценариев

1. Каждая заявка имеет уникальный идентификатор.
2. Каждая завершённая проверка сохраняется с результатом и временем выполнения.
3. Автоматическая оценка не подменяет окончательное решение уполномоченного оператора, если такое решение требуется процессом.
4. Недоступность внешнего сервиса не считается отрицательным результатом проверки.
5. Повторная отправка запроса не должна создавать дублирующие заявки или решения.
6. Изменение статуса выполняется только при допустимом переходе.
7. Решение об одобрении или отклонении должно иметь зафиксированное основание.
8. Операции, влияющие на состояние заявки, должны регистрироваться для аудита.
9. Передача данных в Модули 2 и 3 выполняется после одобрения заявки.
10. Повторная подача после доработки должна сохранять связь с исходной заявкой и историю изменений.
