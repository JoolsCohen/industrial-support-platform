# Системные требования (System Requirements Specification)

## 1. Назначение документа

Документ определяет функциональные и нефункциональные требования к Модулю 1 системы «ГИС Господдержка», предназначенному для автоматизации приёма, проверки и рассмотрения заявок промышленных предприятий на получение государственной поддержки.

Требования устанавливают ожидаемое поведение системы, ограничения доступа, правила обработки ошибок и критерии приёмки.

Документ используется при проектировании API, модели данных, бизнес-процессов и тестовых сценариев.

## 2. Область действия системы

### 2.1. Функции в рамках Модуля 1

- Создание, сохранение и редактирование черновиков заявок.
- Автозаполнение сведений о предприятии по ИНН.
- Валидация данных заявки и бизнес-ограничений.
- Прикрепление документов к заявке.
- Проверка юридического статуса предприятия, налоговой задолженности, процедур банкротства и сведений РНП.
- Получение и обработка результатов скоринговой оценки.
- Автоматическая маршрутизация заявок.
- Просмотр заявок и результатов проверки оператором.
- Одобрение, отклонение и возврат заявки на доработку.
- Повторная подача исправленной заявки.
- Уведомление заявителя об изменении статуса.
- Хранение результатов проверок, скоринга, решений и истории статусов.
- Повторная обработка неуспешных интеграционных операций.
- Передача сведений об одобренных проектах в Модуль 2 и финансовых условий в Модуль 3.

### 2.2. Функции вне рамок Модуля 1

- Разработка и обучение алгоритма внешнего сервиса AI-скоринга.
- Изменение данных государственных реестров.
- Мониторинг исполнения проектов промышленной модернизации в Модуле 2.
- Формирование и проверка отчётности получателей поддержки в Модуле 3.
- Проведение банковских транзакций и фактическое перечисление средств.
- Реализация функциональности внешних реестров и смежных информационных систем.

## 3. Пользователи и роли

| Роль | Функции | Ограничения |
|---|---|---|
| Заявитель | Создание и редактирование собственных черновиков, отправка заявок, загрузка документов, просмотр статуса, исправление заявки после возврата | Не имеет доступа к чужим заявкам и функциям принятия решений |
| Оператор | Просмотр доступных заявок, результатов проверок и скоринга, принятие решений в пределах полномочий | Не может выполнять операции, запрещённые его ролью или текущим статусом заявки |
| Администратор | Управление настройками и доступами в рамках назначенных полномочий | Административная роль сама по себе не даёт права принимать решения по заявкам |
| Системный сервис | Запуск проверок, изменение системных статусов, запись результатов, обработка ошибок и передача данных | Должен соблюдать бизнес-правила, ограничения доступа и требования аудита |

Система должна предоставлять пользователям только те данные и операции, которые необходимы для выполнения их функций.

Идентификатор оператора при фиксации решения должен определяться сервером на основании авторизованной сессии, а не приниматься как доверенное значение из тела клиентского запроса.

## 5. Требования к статусам и переходам

### 5.1. Допустимые статусы

| Статус | Значение |
|---|---|
| `DRAFT` | Черновик заявки |
| `SUBMITTED` | Заявка отправлена |
| `DATA_CHECK` | Выполняются автоматические проверки |
| `NEEDS_REVISION` | Заявка возвращена на доработку |
| `UNDER_REVIEW` | Заявка рассматривается оператором |
| `APPROVED` | Заявка одобрена |
| `REJECTED` | Заявка отклонена |

Статус заявки и рекомендация скорингового модуля являются разными сущностями. Значения `APPROVE`, `MANUAL_REVIEW` и `REJECT` характеризуют рекомендацию скоринга и не должны автоматически использоваться вместо статуса заявки.

### 5.2. Основные переходы

- `DRAFT` → `SUBMITTED`: заявитель отправляет валидную заявку.
- `SUBMITTED` → `DATA_CHECK`: система начинает автоматические проверки.
- `DATA_CHECK` → `UNDER_REVIEW`: проверки завершены без стоп-факторов, и результат скоринга предусматривает ручное рассмотрение.
- `DATA_CHECK` → `REJECTED`: сработал стоп-фактор или скоринговый балл ниже установленного порога учебного сценария.
- `DATA_CHECK` → `DATA_CHECK`: проверка не завершена по технической причине; заявка остаётся в состоянии обработки.
- `UNDER_REVIEW` → `APPROVED`: оператор одобряет заявку.
- `UNDER_REVIEW` → `REJECTED`: оператор отклоняет заявку с указанием основания.
- `UNDER_REVIEW` → `NEEDS_REVISION`: оператор возвращает заявку на доработку.
- `NEEDS_REVISION` → `SUBMITTED`: заявитель повторно отправляет исправленную заявку.

Статусы `APPROVED` и `REJECTED` считаются конечными для данного цикла рассмотрения. Изменение окончательного решения должно выполняться по отдельной согласованной процедуре, если такая возможность предусмотрена проектом.

Недопустимые переходы должны отклоняться. Каждый выполненный переход должен сохраняться в истории статусов.

## 6. Нефункциональные требования

Указанные значения являются целевыми показателями учебного проекта. Их выполнение должно быть подтверждено испытаниями при согласованных условиях нагрузки и эксплуатации.

### 6.1. Производительность

| ID | Требование | Критерий проверки |
|---|---|---|
| NFR-PERF-01 | Время ответа синхронных API-запросов должно составлять менее 1,5 секунды на уровне p95 при согласованной нагрузке | Нагрузочные испытания подтверждают p95 < 1,5 секунды |
| NFR-PERF-02 | Целевой срок обработки заявки должен составлять не более 2 часов при штатной работе внешних интеграций | Метрики обработки подтверждают целевой показатель на согласованном наборе сценариев |
| NFR-PERF-03 | Длительные проверки не должны блокировать пользовательский интерфейс на всё время выполнения | Заявитель получает подтверждение принятия заявки и может просматривать её актуальный статус |

p95 означает, что не менее 95% измеренных запросов укладываются в установленный предел при заданных условиях тестирования.

| NFR-AV-04 | Ошибки интеграций должны быть доступны для мониторинга и диагностики | Система регистрирует ошибки и позволяет выявлять повторяющиеся сбои |
| NFR-AV-05 | Целевой таймаут одной попытки внешнего запроса составляет 10 секунд, если контракт конкретной интеграции не устанавливает иного согласованного значения | Превышение установленного таймаута регистрируется как неуспешная попытка |
| NFR-AV-06 | Для одной логической интеграционной операции допускается не более трёх попыток, включая первоначальную | После трёх неуспешных попыток автоматические повторы прекращаются и фиксируется конечная ошибка |
| NFR-AV-07 | Система должна поддерживать отложенную повторную обработку неуспешных операций | Техническая задача может иметь внутреннее состояние `RETRY_SCHEDULED`, не являющееся бизнес-статусом заявки |
| NFR-AV-08 | Исчерпание попыток внешней проверки не должно приводить к автоматическому отказу только по причине технической ошибки | Заявка остаётся в обработке до согласованного восстановления или ручного разбора |

Интервалы между повторными попытками, правила их настройки и условия ручного восстановления должны быть определены в контрактах интеграций. Приведённые значения используются как проектные допущения, пока не подтверждены результатами анализа интеграций.

### 6.3. Безопасность и персональные данные

| ID | Требование | Критерий проверки |
|---|---|---|
| NFR-SEC-01 | Доступ к защищённым функциям должен требовать аутентификации | Неавторизованный пользователь не может выполнять защищённые операции |
| NFR-SEC-02 | Система должна применять ролевую авторизацию | Пользователь имеет доступ только к разрешённым данным и операциям |
| NFR-SEC-03 | Передача данных между компонентами должна выполняться по защищённым каналам | Конфигурация соединений соответствует принятой политике безопасности |
| NFR-SEC-04 | Обработка персональных данных должна соответствовать применимым требованиям законодательства РФ, включая 152-ФЗ в части соответствующей обработки | Документированы цели, состав данных, основания обработки, доступы и меры защиты |
| NFR-SEC-05 | Пароли, токены и другие секреты не должны попадать в обычные журналы | Проверка журналов не выявляет секретных значений |
| NFR-SEC-06 | Административные функции должны быть защищены отдельными полномочиями | Пользователь без соответствующих прав не может выполнять административные операции |
| NFR-SEC-07 | Система должна обеспечивать контролируемую загрузку документов | Проверяются тип, размер и целостность файла; дополнительные проверки безопасности задаются согласованной политикой |

Доступ к контактным данным и документам заявки должен предоставляться только пользователям, которым эти данные необходимы для выполнения рабочих функций.

### 6.4. Аудит и целостность данных

| ID | Требование | Критерий проверки |
|---|---|---|
| NFR-AUD-01 | Система должна регистрировать значимые действия пользователей и системных сервисов | Для события доступны тип действия, время и субъект |
| NFR-AUD-02 | История изменения статусов и принятия решений должна сохраняться | Предыдущие события доступны для просмотра в рамках полномочий |
| NFR-AUD-03 | Изменение бизнес-данных и фиксация связанного события аудита должны выполняться согласованно | Транзакционные проверки не выявляют несогласованных записей |
| NFR-AUD-04 | Система должна различать отсутствие результата, отрицательный результат проверки и техническую ошибку | Состояния имеют разные значения и не смешиваются в отчётах |
| NFR-AUD-05 | Система должна сохранять историю повторной подачи заявки и изменения её данных | Можно установить последовательность изменений в рамках доступных аудиторских записей |

### 6.5. Сопровождаемость и наблюдаемость

| ID | Требование | Критерий проверки |
|---|---|---|
| NFR-MNT-01 | Ошибки должны содержать информацию, достаточную для диагностики без раскрытия секретов и избыточных персональных данных | По журналам можно определить компонент, время и тип ошибки |
| NFR-MNT-02 | Основные показатели обработки заявок и интеграций должны быть доступны для мониторинга | Измеряются продолжительность обработки, количество ошибок и число незавершённых операций |
| NFR-MNT-03 | Изменения бизнес-правил должны быть документированы и проверяемы | Для изменений определены версия, основание и связанные тесты |
| NFR-MNT-04 | Интеграционные ошибки должны иметь идентификаторы корреляции, позволяющие связать события одной операции | Записи журнала и сведения о попытках позволяют проследить выполнение операции |

### 6.6. Хранение данных

| ID | Требование | Критерий проверки |
|---|---|---|
| NFR-DATA-01 | Сроки хранения заявок, документов, результатов проверок и аудиторских записей должны быть определены отдельно | Для каждой категории данных согласованы срок хранения и порядок удаления или архивирования |
| NFR-DATA-02 | Система должна обеспечивать ссылочную целостность связанных данных | Невозможно сохранить ссылку на отсутствующее предприятие или заявку |
| NFR-DATA-03 | История решений и проверок не должна теряться при повторной обработке заявки | Предыдущие результаты остаются доступными в рамках установленных прав доступа |

## 7. Требования к API

1. API должен соответствовать контракту `docs/03-api/openapi.yaml`.
2. Операции создания, редактирования, отправки и повторной подачи заявки должны соответствовать разрешённым статусам.
3. Валидация данных выполняется на серверной стороне, независимо от проверок пользовательского интерфейса.
4. Ошибки должны возвращаться в согласованном формате с кодом ошибки и понятным сообщением.
5. Для операций, способных создавать дублирующие записи или повторно инициировать бизнес-действие, должна быть определена политика идемпотентности.
6. Повторное использование ключа идемпотентности с другим содержимым запроса должно приводить к конфликту.
7. Пользовательские идентификаторы не должны использоваться для обхода проверки прав доступа.
8. Контракты загрузки файлов, черновиков и повторной подачи должны быть отражены в OpenAPI до завершения тестирования.
